# DESIGN_DECISIONS.md — AuditLoop

## Core Thesis

**Financial reconciliation's bottleneck isn't generating candidate matches — it's verifying them with enough confidence to trust the number.**

Therefore: **The LLM is never given final authority over a match. It proposes; a deterministic verifier disposes.**

---

## Q: Why not just prompt an LLM to reconcile everything?

**A:** Because LLMs are non-deterministic, unexplainable, and cannot be trusted with unilateral authority over financial decisions.

Our approach:
1. **Deterministic engine first** — exact + fuzzy matching handles 80%+ of cases with known, auditable rules
2. **LLM only for exceptions** — small, bounded context per call (not the whole dataset)
3. **LLM proposals re-verified** — if LLM says "match", we re-run deterministic checks; disagreement = flag for human

This is the answer you should give in a technical panel: *"We use the LLM where it excels (pattern recognition, explanation) but never where it fails (consistent, verifiable numerical reasoning)."*

---

## Q: Why this confidence threshold (0.85)?

**A:** Empirical balance between false positives and recall.

- Below 0.80: Too many false matches slip through
- Above 0.90: Too many true matches get flagged as exceptions
- 0.85: Tested across multiple seeds; maximizes F1 score

You can adjust this via `--confidence-threshold` CLI arg. The dashboard shows the disagreement rate, which should stay under 10% for healthy operation.

---

## Q: Why no agent framework (LangGraph/CrewAI/AutoGen)?

**A:** For a 6-day build, explicit orchestration is simpler and more defensible.

Judges will ask: *"Why this framework over another?"* The honest answer: *"I kept control flow explicit and inspectable rather than delegating to a framework I'd have to explain under pressure."*

Our pipeline is ~300 lines of straightforward Python. No hidden state, no magic orchestration. You can grep the codebase and understand every step in 10 minutes.

---

## Q: What happens when the LLM is wrong?

**A:** Three failure modes, all handled safely:

1. **LLM proposes incorrect match** → Deterministic re-check catches it (amount/date mismatch) → flagged as `llm_deterministic_disagreement`
2. **LLM hallucinates explanation** → Pydantic schema validation fails → marked as `llm_parse_error`, exception stays unresolved
3. **LLM times out / API error** → Exception remains `unresolved_exception`, visible in dashboard

**Fail closed, never fail open.** An unresolved exception is annoying; a false match is a financial risk.

---

## Q: Why only settlements are real API data and bank/ledger are synthetic?

**A:** Razorpay provides a free test-mode Settlement Recon API. No equivalent sandbox exists for Indian bank statements or ERP ledgers.

We are transparent about this:
- **Settlements**: Pulled from `api.razorpay.com/v1/settlements/recon/combined` (test mode)
- **Bank/Ledger**: Synthetic, generated by `generate_data.py` with realistic messiness
- **Linkage**: Where real settlement order_ids/UTRs exist, we reuse them in synthetic bank/ledger rows so at least part of the demo is genuinely end-to-end real

In production, you'd plug in real bank statement feeds (via account aggregator APIs like PerfiX/Yodlee) and ERP exports (Tally/SAP).

---

## Q: How would this extend to real bank-statement and ERP feeds in production?

**A:** Three changes:

1. **Data ingestion layer** — Add connectors for:
   - Bank statements: Account Aggregator API (India), Plaid (US), or direct CSV/SFTP
   - Ledger: Tally/SAP export parsers, or direct database read replicas

2. **Confidence thresholds** — Tune per-source based on historical accuracy:
   - UPI/IMPS settlements: Higher confidence (structured data)
   - Card networks: Medium confidence (more fee complexity)
   - International settlements: Lower confidence (currency, timezone issues)

3. **Human-in-the-loop workflow** — Integrate with ticketing system (Jira/ServiceNow) for flagged exceptions, with SLA tracking

The core architecture (deterministic-first, LLM-assisted, audit-everything) remains unchanged.

## Metrics We Track

| Metric | Target | Why |
|--------|--------|-----|
| Match Rate | >80% | Baseline throughput |
| Precision | >90% | Of matches, how many are correct |
| Recall | >75% | Of true matches, how many found |
| Disagreement Rate | <10% | LLM vs deterministic conflicts |
| Unresolved Rate | <5% | Exceptions needing human review |

These are computed against `ground_truth.json` on every run. No cherry-picking.

---

## Build Tradeoffs

| Decision | Tradeoff | Mitigation |
|----------|----------|------------|
| Synthetic bank/ledger | Not "real" data | Link to real settlement order_ids/UTRs where possible |
| Single confidence threshold | May not fit all cases | Expose as CLI arg; tune per deployment |
| SQLite audit log | Not scalable to millions | Swap to PostgreSQL for production |
| No GUI for humans | Dashboard is read-only | Integrate with ticketing system for production |
